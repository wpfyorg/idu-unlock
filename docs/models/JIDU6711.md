# JIDU6711: unlock and back up

The JIDU6711 is a Qualcomm `6j11` router, in the same firmware branch as the
JIDU6111, JIDU6411, JIDU6611, JIDU6811, and JIDU6911. This page covers what is
verified on the model — detection, root SSH, and backup — and the current state
of OpenWrt flashing, which is not verified.

> [!IMPORTANT]
> **Verified: root SSH and backup.** A user report on
> [PR #15](https://github.com/wpfyorg/idu-unlock/pull/15#issuecomment-6725303723)
> confirms that unlock and backup work on a JIDU6711 without any issue.
> **Not verified: OpenWrt flashing.** No JIDU6711 install has been reported, and
> `./flash.sh flash` stops on this model instead of installing.

| | |

## Detect the model

Detection reads the device flags the router returns at login and changes
nothing:

```bash
./flash.sh detect
```

On macOS and Linux, `./flash.sh detect` prints `JIDU6711` as the model and
`qualcomm` as the family. On Windows:

```powershell
.\flash.ps1 detect
```

Then check the firmware, which is read-only too:

```bash
./flash.sh check
```

`JIDU6711` takes the `6j11` branch, so `check` reports `YES` through `R3.2.6`
and `TEST` for `R3.2.7` and newer. The report that confirms this page did not
include the firmware version, so run `check` on your own unit and keep the
result next to your notes. [Checking firmware
compatibility](../../README.md#checking-firmware-compatibility) explains the
three states.

## Unlock root SSH

The router must be set up, not factory-fresh: a reset unit keeps the API locked
until the setup wizard finishes and sets the admin password.

On macOS and Linux, with an RSA key you want installed for root:

```bash
ssh-keygen -t rsa -b 2048 -f ~/.ssh/idu_rsa     # skip if you have one
./flash.sh unlock --key ~/.ssh/idu_rsa
```

Dropbear on these builds can reject Ed25519 keys, so use RSA. Without `--key`
the unlock still works and leaves root passwordless; the script prints the
`ssh root@192.168.31.1` hint when it finishes. If the command reports it cannot
bind port 80 on macOS or Linux, run it with `sudo`.

On Windows:

```powershell
ssh-keygen -t rsa -b 2048 -f $HOME\.ssh\idu_rsa
.\flash.ps1 unlock --key $HOME\.ssh\idu_rsa
```

Windows Firewall has to allow Python to receive the router's callback, and WSL2
cannot receive it, so use `flash.ps1` from Windows. More detail:
[docs/WINDOWS.md](../WINDOWS.md).

Verify the session before going further:

```bash
ssh -i ~/.ssh/idu_rsa root@192.168.31.1
```

If the unlock reports that the method did not land, `check` says `NO`, or the
firmware predates the password-history feature, use the offline
[`breeze` route](../BREEZE.md) when the web UI still has **Backup Settings** and
**Restore Settings**. UART is the last fallback:
[UART recovery](../../OPENWRT.md#route-b-uart-recovery-u-boot-over-serial).

## Back up the stock firmware

This is the verified step, and the one to run before anything else touches the
flash:

```bash
./flash.sh backup
```

The command unlocks first if needed, then writes a directory named after the
Wi-Fi network:

```text
AirFiber-XXXXXX/
├── credentials.txt
├── uboot_credentials.env
├── partitions.txt
├── uboot_env.txt
├── factory_env.txt
└── backup/
    ├── mtd1_BL2.bin
    ├── mtd5_ubi.bin
    └── ...
```

Keep the directory private: it holds Wi-Fi passwords, factory credentials,
serial data, bootloader data, and raw partitions. `docs/BACKUP.md` covers
`--full-chip` and the rest: [Make a backup](../../README.md#make-a-backup).

## Flashing: not verified

The automated command does not install OpenWrt on a JIDU6711. The model has no
image set registered in `flash.sh`, so this:

```bash
./flash.sh flash
```

stops with `no OpenWrt image set is registered for model: JIDU6711` before it
downloads or writes anything. `./flash.sh download` stops the same way. That is
deliberate: no one has reported a completed install on this model, and a failed
flash on a `6j11` unit needs UART to recover.

The manual route exists and is the same community build as the other `6j11`
models:

- [Installing OpenWrt by hand](../../OPENWRT.md#qualcomm-6j11-jidu-6111--6411--6611--6811--6911)
  has the procedure, the reasoning, and the recovery steps.
- The [JIDU6611 page](JIDU6611.md#route-a-ssh-mayank-method-primary) spells out
  the same commands with the `6j11` image names filled in.

Treat those commands as untested on a JIDU6711. If you run them, keep the
backup above, have a 3.3 V UART adapter ready, and do not copy `mtdN` numbers
from another unit: read `/proc/cmdline` and `/proc/mtd` on your own router.

If you complete an install, or a step fails in a new way, report it on the
[issue tracker](https://github.com/wpfyorg/idu-unlock/issues) with the model,
the firmware version, and the output. That report is what turns this section
into a tested route.
